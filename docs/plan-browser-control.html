1. Overview & Goals

Problem Statement

Playwright provides headless browser automation but cannot access personal browser sessions (cookies, logins). We need a solution that lets Eliezer control the user's actual Chrome/Firefox browser remotely.

Solution

A Chrome extension that communicates exclusively through the Clawchat web app tab via postMessage. The extension never talks to the server directly — the web app relays commands and results. The web app tab being open is the consent mechanism: close the tab, kill the connection.

Key Principle: Zero extension auth. The web app is already authenticated. The extension is a dumb executor that only listens to the web app page. No tokens, no JWTs, no revocation — closing the tab severs all control.

Components

1

Chrome Extension

Dumb executor. No server awareness, no auth. Listens for commands from content script via chrome.runtime.sendMessage, executes on target tabs, returns results.

2

Clawchat Web App

The relay. Receives tool_remote_exec messages via existing SSE, forwards to extension via postMessage on the page. Receives results back the same way, POSTs them to server. Already authenticated — no new auth needed.

3

Clawchat Server

Existing infrastructure. No new endpoints, no new event types. Commands flow as tool_remote_exec messages via POST /send. Responses flow as tool_remote_exec_response messages via POST /api/messages. Both are just messages — Clawchat doesn't need to know what's inside.

4

Eliezer

New tool: browser_control. Sends commands via chat.send('default', payload, 'tool_remote_exec'). Awaits incoming chat:user_message with type: tool_remote_exec_response matching command ID.

4. Communication Protocol

All communication reuses existing infrastructure. No new server endpoints. Two new message/event types on existing channels.

Command path (Eliezer → Extension)

Eliezer sends via existing chat.send() with type tool_remote_exec. Server pushes to web app via existing SSE. Web app relays to extension via postMessage → content script → chrome.runtime.sendMessage.

// Eliezer sends command chat.send('default', JSON.stringify({ commandId: "cmd-123", action: "navigate", params: { url: "https://linkedin.com" } }), 'tool_remote_exec');
// Web app receives via SSE, relays to extension window.postMessage({ type: 'ELIEZER_COMMAND', commandId: "cmd-123", action: "navigate", params: { url: "https://linkedin.com" } }, '*');

Response path (Extension → Eliezer)

Extension sends result back via chrome.runtime.sendMessage → content script → postMessage → web app. Web app POSTs to /api/messages — the same endpoint used for regular user messages. Clawchat pushes it to Eliezer as a normal chat:user_message event. Eliezer checks for type field to distinguish from regular messages.

// Web app forwards result as a message fetch('/api/messages', { method: 'POST', body: JSON.stringify({ type: 'tool_remote_exec_response', content: { commandId: "cmd-123", status: "success", result: {...} } }) });

Eliezer tool (awaiting response)

// browser_control tool async call({ action, params }) { const commandId = crypto.randomUUID(); const promise = this.waitForMessage('tool_remote_exec_response', commandId, 30_000); await chat.send('default', JSON.stringify({ commandId, action, params }), 'tool_remote_exec'); const result = await promise; return result; }

The message body is a discriminated union: if it has type, it's a typed event; otherwise it's a regular { content } user message. Clawchat doesn't need to know the difference — it just pushes messages through. Any future remote tool can use the same pattern.

5. Security Model

Principle: Web app tab open = consent. Close the tab = kill all control. No tokens, no sessions, no revocation.

Authentication

None for the extension. The extension never talks to the server. All server communication goes through the web app, which is already authenticated. The extension only receives commands via postMessage from the clawchat page.

Consent Model

Control Description
Tab open = active Browser control only works while the clawchat web app tab is open
Close tab = kill Closing the web app tab immediately severs all control
Visual indicator Green border on controlled tab when Eliezer is active
Site blacklist Extension ignores commands for blacklisted domains (banking, email)

Attack surface

  • Extension content script runs on clawchat page — postMessage origin check is critical
  • Extension has no secrets to leak — worst case, a compromised extension executes browser commands while the tab is open
  • Extracted page content is untrusted — must go through vetContent() before reaching the agent

8. Integration Points

No new server endpoints. Two new message types on existing channels:

What Channel Message type
Command (Eliezer → extension) Existing POST /send tool_remote_exec
Response (extension → Eliezer) Existing POST /api/messages tool_remote_exec_response

Web app changes

  • Listen for tool_remote_exec messages on SSE, relay to extension via postMessage
  • Listen for ELIEZER_RESULT postMessages from content script, POST to /api/messages as { type: "tool_remote_exec_response", content: ... }
  • Extension detection: ping via postMessage, show status indicator

Content script bridge

// content-bridge.js (injected on clawchat page) window.addEventListener('message', (event) => { if (event.source !== window) return; if (event.data.type === 'ELIEZER_COMMAND') { // Relay command to background script chrome.runtime.sendMessage(event.data, (response) => { window.postMessage({ type: 'ELIEZER_RESULT', ...response }, '*'); }); } });
